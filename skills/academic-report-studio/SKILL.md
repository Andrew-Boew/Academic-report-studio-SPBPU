# Academic Report Studio

Execute laboratory work reproducibly and create evidence-based academic reports in `.docx`. Treat the user's assignment and methodical instructions as the implementation contract. Never invent experiments, results, citations, measurements, code behavior, or personal data.

## Required workflow

1. Inventory the project folder before drafting:

   ```bash
   python scripts/inspect_project.py /absolute/input/folder --out /absolute/work/inventory.json
   ```

2. Read the self-contained [references/layout-profile.md](references/layout-profile.md), [references/format-standard.md](references/format-standard.md), [references/structures-and-writing.md](references/structures-and-writing.md), [references/natural-academic-writing.md](references/natural-academic-writing.md), [references/formulas-and-pagination.md](references/formulas-and-pagination.md), and [references/spacing-and-layout-from-examples.md](references/spacing-and-layout-from-examples.md). The last three files are mandatory for every report: use them to produce natural evidence-linked prose, genuine Microsoft Word equations, exact sample-confirmed paragraph rhythm, intact long values, and defect-free page transfers. For laboratory work, also read [references/lab-automation.md](references/lab-automation.md). If the user asks to perform, implement, calculate, complete, or test the laboratory itself, read [references/execute-lab.md](references/execute-lab.md) and finish its execution gate before drafting the report. If the assignment or report contains an algorithmic flowchart, program flowchart, data flowchart, system flowchart, or a user calls a diagram a `блок-схема`, read [references/flowcharts.md](references/flowcharts.md) completely before drawing it; do not substitute a generic boxes-and-arrows picture or UML activity notation. Read [references/spec-format.md](references/spec-format.md) before building the DOCX. These bundled rules are sufficient; never require an old report or a machine-specific source path.
3. Load stable title-page details from `.report-profile.json` and discipline-specific reviewer details from `.report-subjects.json` in the project folder or its parent, if present. The bundled `assets/report-profile.default.json` contains only the confirmed institutional header and city; its student name and group are empty. The bundled `assets/report-subjects.default.json` is empty and must never supply a reviewer or discipline. Then extract work details from the current assignment. Before drafting, explicitly resolve the report type (`lab` or `course`) because it changes the title-page work label. Resolve the rest of the intake checklist and ask one compact grouped question only for fields that remain missing.
   Resolve the final DOCX destination at the same time. An explicit destination file or folder supplied by the user has priority. Otherwise save the final DOCX beside the primary assignment or methodical file. If no methodical file is available, save it in the user-supplied materials or project folder. Never leave the only final copy in a temporary work/render directory or silently redirect it elsewhere because the preferred destination is not writable.
4. Classify each prospective statement as `provided`, `computed`, `observed`, `inferred`, or `missing`. Write only the first four; label material inferences. Ask a follow-up only when missing information blocks a correct report.
5. Resolve requirements in this order:
   - explicit user instructions and the current assignment;
   - verified applicable GOST requirements summarized in `references/format-standard.md`;
   - faculty/department methodical instructions and supplied templates, where they supplement rather than contradict GOST;
   - the bundled layout profile, which stores the user's confirmed visual and institutional conventions without depending on source reports;
   - generic academic convention.
6. Determine whether the request is `report-only` or `execute-and-report`, and whether the work is a laboratory report or course paper. If the type is not explicit and cannot be read from the assignment, ask: `Какой вид отчёта нужен: лабораторная работа или курсовая работа?` The type changes the title page; the body follows the actual assignment rather than a generic type template. If intent is ambiguous but the user says `сделай лабораторную`, `выполни лабу`, or equivalent, select `execute-and-report`.
7. In `execute-and-report` mode, convert every methodical requirement into an acceptance criterion, implement the work in the user-designated project folder, run the specified toolchain and tests, and collect real outputs. Preserve unrelated user changes and do not replace an existing solution wholesale when a targeted edit is sufficient. Do not start report prose until the execution gate in `references/execute-lab.md` is satisfied or an exact blocker has been reported.
8. Analyze datasets and code reproducibly. Preserve source inputs. Record formulas, filters, units, sample sizes, random seeds, exclusions, commands, tool versions, and transformations needed to reproduce every reported result.
9. For a course paper only, verify every prospective bibliography source by opening its direct public HTTPS page. Record authors/organization, title, publication, year, and DOI/URL from the source or publisher page rather than a search-result snippet. Do not treat the current assignment, a local methodical PDF, project files, generated output, an AI answer, or another student's report as a bibliographic source. A laboratory report must contain neither a bibliography block, external hyperlinks, nor numeric literature citations such as `[1]`.
10. Create a JSON document specification following `references/spec-format.md`. Supply heading text without numeric prefixes: the builder creates real Word multilevel numbering. Apply the opening-page contract from `references/layout-profile.md`: place `Введение` when required, `Цель работы`, and `Задачи` on the same first body page; start `Ход работы`, `Дополнительные задания`, and `Выводы` on separate new pages. Do not insert a page break between opening blocks. Before building, pass the universal implementation-depth gate in `references/structures-and-writing.md`, the structure, evidence-density, cohesion, naturalness, and anti-template gates in `references/natural-academic-writing.md`, and the formula/pagination preflight gate in `references/formulas-and-pagination.md`. Store every displayed formula as LaTeX in an `equation` block so the builder creates native OMML; never imitate a formula with italic text, Unicode subscripts, slash fractions, tabs, spaces, or an image. The main part must explain how the current work was actually made, not merely restate the assignment or show final results. For every programming report, fill `document.code_change` and pass the source-listing coverage gate from `references/spec-format.md`: new or rewritten code requires the complete final source; refactoring requires both the complete original and complete refactored source; tests and task-specific program experiments require their own complete listings. Put these listings in traceable appendices rather than substituting a project-folder link or selected fragments.
11. Build only a `.docx`:

   ```bash
   python scripts/build_report.py --spec /absolute/work/report-spec.json --profile /absolute/project/.report-profile.json --subjects /absolute/project/.report-subjects.json --output /absolute/output/report.docx
   ```

   Omit `--profile` or `--subjects` only when the specification already contains the corresponding title-page fields or declares `profile_path` / `subject_profile_path`.

12. Run structural validation on the draft:

   ```bash
   python scripts/validate_report.py /absolute/output/report.docx --json /absolute/work/validation.json
   ```

13. Render the draft with PDF emission, then materialize the accurate cached contents from the real rendered pages:

   ```bash
   python scripts/render_docx.py /absolute/output/report-draft.docx \
     --output_dir /absolute/work/rendered-draft --emit_pdf

   python scripts/finalize_toc.py /absolute/output/report-draft.docx \
     --spec /absolute/work/report-spec.json \
     --rendered-pdf /absolute/work/rendered-draft/report-draft.pdf \
     --output /absolute/output/report.docx \
     --entries-json /absolute/work/toc-entries.json
   ```

   Re-render the finalized DOCX. If the materialized contents changed pagination, run the finalizer once more with the latest PDF until the entry/page mapping is stable. Never deliver the placeholder `Обновите содержание в Word`.
14. Re-run structural validation on the finalized DOCX, inspect every rendered page at 100%, and iterate until there are no clipped elements, broken tables, blank accidental pages, incorrect ordering, stale placeholders, unreadable figures, or unjustified half-empty pages. Verify the chapter-break contract on the rendered PDF: all present opening blocks (`Введение`, `Цель работы`, `Задачи`) share the first body page; `Ход работы`, `Дополнительные задания`, and `Выводы` each begin at the top of a new page. Apply the page-density gate from `references/layout-profile.md`: outside the cover, contents, the intentionally isolated opening page, an intentional new appendix, and the natural last page, a page whose content ends above roughly 60% of the usable height is a layout defect until its cause is identified and corrected. Remove unnecessary forced breaks, release over-broad `keep_with_next`, compact or reposition figures and tables, and reorganize nearby text; never pad the page with filler. Perform the final prose audit from `references/natural-academic-writing.md`: remove duplicated claims, generic openings, unsupported evaluations, excessive nominalizations, repetitive paragraph starts and mechanical transitions while preserving exact technical meaning. Apply every formula-structure, inline-math, semantic-break, table-transfer, long-number, density, spacing-matrix, and header-word gate from `references/formulas-and-pagination.md` and `references/spacing-and-layout-from-examples.md` to the actual rendered pages. For every table, verify native Word pagination: keep one logical table object, repeat its first row with `w:tblHeader`, prevent row splitting with `w:cantSplit`, and allow exact long values to wrap naturally inside their cells. Reject manual page breaks, `rows_per_page`, whole-table `keep_with_next`, `w:noWrap`, landscape sections, clipped values, and split header words. For every flowchart or UML activity diagram, apply the semantic, routing, text-fit, arrowhead, connector, page-split, and node-scale gates from `references/flowcharts.md`. For every programming report, compare the rendered appendices against `document.code_change`: every declared original, final, test, and supporting source file appears once as a complete appendix listing with a visible relative filename; no required file is represented only by a fragment or omitted because the project is submitted separately. The render is QA only; deliver the DOCX, not the PDF or page PNGs.
15. After the final DOCX has passed validation and visual QA and exists at the resolved destination, remove task-created drafts, superseded DOCX versions, temporary PDFs, rendered PNG pages, TOC JSON, validation JSON, extracted text, transient screenshots, and build/test logs that are not required deliverables. Use `scripts/cleanup_report_work.py --apply` with explicit final and work paths, or perform an equally narrow cleanup. Preserve the final DOCX, completed source project, user-supplied inputs, real evidence explicitly required as a project deliverable, profiles, and any pre-existing files. If final validation fails or the destination copy is missing, do not clean up evidence needed to continue.

## Autonomous and cross-platform operation

- Resolve every bundled reference and script relative to this `SKILL.md`; never use a remembered absolute installation path.
- The skill does not require any previous user report. `references/layout-profile.md` is the complete visual contract.
- Prefer the active Python runtime; otherwise try `python3`, Windows `py -3`, then `python`. Check core dependencies from `requirements.txt` before work. Create a project-local virtual environment only when needed and obtain approval before downloading packages.
- Use bundled `scripts/render_docx.py` for DOCX-to-PDF/PNG QA. It detects LibreOffice on Windows, macOS, and Linux, then uses installed PyMuPDF or `pdftoppm`; install `requirements-render.txt` only if neither rasterizer is available. Treat a missing office converter as a visual-QA blocker, not as permission to skip verification silently.
- Use `pathlib`-style paths in generated code, quote paths passed to commands, and do not embed a username, home folder, drive letter, or OS-specific separator in the completed laboratory project.
- When the assignment does not mandate a platform, make the implementation and run instructions usable on Windows, macOS, and Linux. When it does, follow the mandated platform and state the limitation accurately.

## Final output location

Resolve the destination before building and apply this priority order:

1. An exact output file or destination folder explicitly supplied by the user.
2. The directory containing the primary methodical/assignment file used for the current report.
3. The materials or project directory explicitly supplied by the user when no methodical file is available.

When the user provides a folder rather than a file, inspect it recursively enough to identify the primary methodical file and save the final DOCX in that file's own directory, not automatically in the scan root. Keep drafts, JSON, PDFs, PNG renders, logs, and temporary artifacts in one dedicated task work directory; copy or move only the validated final DOCX to the resolved destination, then delete that task work directory after successful final QA. If the destination is not writable, request the required permission and preserve the intended path; do not choose a different folder without telling the user. Apply the existing no-overwrite rule when a DOCX with the target name already exists.

## Intake checklist

Resolve these fields before final assembly. Reuse verified profile values; never guess them:

- student: full name exactly as it must appear, group;
- reviewer for the current discipline: full name, academic/official position, and the preferred role label (default `Проверил:`);
- work: laboratory/course type (ask explicitly when not known), number, title, discipline, variant;
- organization: university, institute, higher school/department;
- title footer: city and year;
- evidence: assignment/methodical file, datasets, source code, screenshots, required calculations, and destination folder.

If required details are missing, ask in one message using this compact form:

> Для титульного листа и отчёта пришлите, пожалуйста: 1) вид отчёта — лабораторная или курсовая; 2) ФИО студента; 3) группу; 4) ФИО преподавателя; 5) должность преподавателя; 6) дисциплину; 7) номер и тему работы; 8) вариант, если есть. Остальное возьму из задания, датасетов и подтверждённого профиля.

Offer to save stable student/organization fields in `.report-profile.json` and reviewer fields keyed by discipline in `.report-subjects.json` beside the user's lab folders. Never store a reviewer in the global profile. Do not save personal data outside the user-selected local folder and do not overwrite an existing profile without permission.

## Non-negotiable rules

- Produce `.docx` only as the final report.
- Save the validated final DOCX in the resolved destination: the user-specified folder/file first, otherwise beside the primary methodical file, otherwise in the supplied materials/project folder.
- In `execute-and-report` mode, also deliver the completed source project and real test/build artifacts requested by the assignment; `.docx` exclusivity applies to the report format, not to source-code deliverables.
- Always include the university title page. Use the bundled SPbPU institutional header unless the current assignment or official university template supplies replacement details. Never infer the student, group, reviewer, or discipline from the bundled files.
- Hide the number on the title page and start the displayed numbering at 1 on the first contents page.
- Keep the opening material on one first body page: `Введение` when required by the report structure, `Цель работы`, and `Задачи`. Do not force a break between these blocks. Start the level-1 sections `Ход работы`, `Дополнительные задания`, and `Выводы` on new pages; their level-2 subsections continue normally without automatic breaks.
- Keep the first-line indent at exactly 1.25 cm, the alignment justified (по ширине), and the line spacing at 1.5 throughout ordinary body text unless the current official template explicitly overrides it. Set ordinary paragraph spacing before/after to 0 pt. Apply the full role-by-role interval matrix from `references/spacing-and-layout-from-examples.md`; never create vertical rhythm with empty paragraphs.
- Require the student's full name and group plus the reviewer's full name and position for the title page. Do not finalize a cover with blank identity fields.
- Never silently fabricate missing values or claim an unperformed experiment.
- Write in a natural, restrained student voice grounded in the student's actual implementation. Prefer concrete explanations of choices, commands, inputs, failures, fixes, and observed outputs over generic academic filler. Vary sentence structure only for readability; never deliberately evade AI detectors, imitate another student's work, insert artificial mistakes, or make false claims of human authorship.
- Give the implementation itself enough space in every laboratory report, regardless of discipline. Derive the explanation from real artifacts and cover, where applicable: decomposition of the solution; chosen data structures, formulas, equipment, parameters, or processing stages; the step-by-step algorithm; important implementation decisions and their reasons; validation and error handling; integration between components; and how each key part was tested. Use exact names from the current work. Do not satisfy this rule with generic theory, a line-by-line listing retell, inflated wording, or invented design motives.
- Apply a coverage gate rather than an arbitrary page count: every mandatory requirement must map to a described implementation element and to evidence of its result. From the main text, the reader must be able to answer: what was made, how it works, why the essential decisions were chosen, what happens at boundaries or failures, and how the behavior was verified.
- Make the work defensible at an oral check: every substantive paragraph, formula, code fragment, table, and conclusion must be explainable from the project and evidence. Avoid unexplained sophistication beyond the assignment and the implemented solution. Include a concise defense brief when useful: key design decisions, likely questions, and factual answers derived from the completed work.
- Never claim that the laboratory is complete merely because code was written. Completion requires the methodical acceptance criteria, a successful required build/run, and observed test evidence. If execution is impossible, return a precise blocker and do not manufacture substitute output.
- Implement only the assigned variant and mandatory scope. Perform optional or bonus tasks only when the user explicitly requests them or the methodical instructions make them mandatory.
- Do not submit work to an LMS, email it, publish it, push it to a remote repository, purchase services, or change external systems without separate explicit authorization.
- Apply a truthfulness gate before drafting and again before delivery: every material factual claim, number, result, table, figure, conclusion, and citation must trace to a supplied file, an opened verified source, an observed program run, or a reproducible calculation. Omit `missing` claims and explicitly qualify `inferred` claims.
- Never write `получено`, `измерено`, `проверено`, `программа выдала`, or an equivalent factual-result phrase unless the corresponding output was actually observed in the current materials or execution log.
- When evidence is insufficient, stop that part of the report, state exactly what is missing, and request it. Do not fill gaps with plausible values, generic outcomes, invented screenshots, fabricated citations, or results copied from another work.
- Never state causal conclusions from correlation alone.
- For a course paper, include a bibliography with at least one genuine publication or authoritative material: a book, peer-reviewed or publisher-hosted article, conference paper, standard, official documentation, official institutional web resource, or published dataset. Every item must have a direct public HTTPS link and must be opened and verified before inclusion. Do not add a bibliography to a laboratory report.
- Do not include the current laboratory assignment, local methodical file, local source-code file, generated report, screenshot, search-results page, AI response, forum post, arbitrary blog, or another student's report in the bibliography. Refer to the assignment in prose as `задание` or `методические указания` without assigning it a bibliography number.
- In a course paper, external hyperlinks are allowed only inside bibliography entries and must lead directly to the verified source, DOI landing page, publisher, standards catalogue, official documentation, institution, or dataset page. Numeric citations `[N]` in course-paper prose must link internally to item N and directly support the statement. A laboratory report uses neither source hyperlinks nor `[N]`; internal Word hyperlinks used by the table of contents remain allowed in both types. Never hyperlink a local path or generated artifact.
- Do not expose secrets, tokens, credentials, private keys, or unnecessary personal data found in files or code.
- Keep the course-paper order `title page → contents → main text → conclusions → sources → appendices`. For a laboratory report use `title page → contents → main text → conclusions → appendices`, with no source list, unless the assignment explicitly requires another order and the user confirms the conflict.
- Do not produce a generic report that could fit another laboratory. Write original text tied to the current assignment, variant, source code, data, and observed results.
- Use real Word heading styles, list numbering, captions, tables, page-number fields, and a TOC field. Link `Heading 1`, `Heading 2`, and `Heading 3` to one real Word multilevel numbering definition with labels `1.`, `1.1.`, and `1.1.1.`. Never type chapter or subchapter digits into heading text; the JSON contains only `Цель работы`, not `1. Цель работы`.
- Put `Таблица N — Название` above the table in the center and `Рисунок N — Название` below the figure in the center. Use Times New Roman 14 pt, 1.5 line spacing, 0 pt before/after, an em dash, and no final period.
- Use 1.5 line spacing in figure captions with 0 pt before/after. Give the centered image paragraph 0 pt before/after and keep image and caption together. Add no empty line: the normal 1.5-line paragraph rhythm supplies the separation confirmed by the retained examples.
- Format every report table with a white background, thin black borders, Times New Roman 14 pt, 1.5 line spacing, 0 pt before/after, and bold headers. Center every numeric index and numeric value horizontally and vertically; keep left alignment only for genuinely narrative cells. Never change a data column to Courier New, reduce it to 9–12 pt, compress characters, or switch it to single spacing merely because values are long. Use a two-column `iteration | value` structure and widen the value column. Keep all pages portrait; allow Word to wrap exact long values naturally inside a centered cell without inserting spaces or changing digits. Never use `w:noWrap` or `w:tcFitText` for these values.
- Match the bundled title composition: ministry; full legal organization type; university name in guillemets; institute; higher school in bold. Then place work type/title/discipline at 14 pt, student and reviewer blocks with names at the right edge, an italic centered `<подпись>` line under each block, no invented date, and city/year at the bottom. Use `Лабораторная работа № N` or `Курсовая работа`.
- Use 3.0 cm left, 1.5 cm right, 2.0 cm top, and 2.0 cm bottom margins. Place page numbers at the bottom right.
- Use sentence case in headings: Word displays `1. Цель работы`, while the stored heading text is `Цель работы`. Do not use all caps or `Цель и задачи работы`. Level 1 is Times New Roman 16 pt bold; level 2 is 14 pt bold; level 3 is 14 pt bold italic. In the main text, every numbered level (`1.`, `1.1.`, `1.1.1.`) uses the same positions: the number begins 1.25 cm from the left text boundary and subheadings do not accumulate an additional indent per level. Keep the `Heading 1–3` style indents at 0; on each generated numbered heading paragraph set direct left indent to 0 cm and first-line indent to 1.25 cm so Word and LibreOffice use the same number position. Keep the multilevel numbering definition linked to the heading styles; never add another style indent. Center only unnumbered structural headings such as `Содержание`, the source list, and `Приложение …`, with both indents 0 cm.
- For a table transferred to another page, keep one native Word table, prevent row splitting, and repeat the header automatically. Mark every header-cell paragraph `keep_with_next`, so the first occurrence of the header stays with at least the first data row; a page containing only the caption and header is a defect. Do not add manual `Продолжение таблицы N` captions or page breaks unless current faculty instructions explicitly require separate physical parts.
- Number tables, figures, and formulas independently and consistently. Do not allow duplicated or skipped numbers.
- Create mathematical notation as native editable Microsoft Word equations (`m:oMath`/OMML) in Cambria Math 14 pt. Put exactly one independent equation, equality, or parameter value in each formula paragraph; never group `d`, `x`, `y`, the Bezout check, input parameters, or different `k` values into a matrix, `aligned`, or equation array. Center every unnumbered paragraph geometrically. A numbered equation uses a center tab at exactly half the usable width and a right tab at the usable right edge: insert a leading tab, the single OMML object, a second tab, then `(N)`. Never reduce a formula below 14 pt. If an exact integer does not fit at 14 pt, preserve it through named high and low decimal blocks, for example `x_1`, `x_0`, followed by `x=x_1\cdot10^{40}+x_0`; keep each definition in its own centered OMML paragraph. Never split a numeric token visually, insert spaces, compress characters, or clip it. Use structural subscripts, superscripts, roots, fractions, limits, matrices, cases, accents, and operators; never substitute styled plain text, slash fractions, Unicode pseudo-indices, screenshots, or formula images. Keep 1.5 line spacing and 0 pt before/after.
- Prevent defective transfers: never allow a caption, formula lead-in, equation number, table header, or one-row continuation to remain by itself. For data with very long integers or identifiers, use narrow two-column sequence tables or separate aligned formula lines instead of compressing several long values into adjacent columns.
- Keep source code readable. Put short fragments in a thin black one-cell frame with a centered caption above (`Листинг N — Название`), Courier New 12 pt by default or 11 pt only when needed after render inspection. Put full listings in appendices without a frame, Courier New 10 pt, single spacing.
- Treat appendices as mandatory whenever code was created, generated, rewritten, refactored, or materially modified for the work. A new or rewritten program includes the complete final source; a refactoring includes the complete original source and the complete refactored source in separate labeled appendices; written tests and additional program experiments are included in their own appendices. Include every authored or materially modified source file needed to reproduce the result, with a visible relative filename before each file. Exclude only generated files, dependencies, build output, caches, binaries, secrets, and unchanged third-party code, and record the exclusion internally. A separately delivered project folder never replaces these listings. Start each appendix on a new page after the source list in a course paper and immediately after conclusions in a laboratory report; use consecutive Cyrillic letters (`Приложение А`, `Приложение Б`, …).
- For testing evidence, prefer a real supplied screenshot. If the project can be executed safely, run the documented command and create a legible image from its literal captured output; preserve the command, test names, result, and exit status without inventing lines. Refer to it naturally in the prose as a numbered figure. If execution and a real screenshot are both unavailable, leave an empty bordered area with a normal numbered figure caption: never place instructions such as «вставьте рисунок» or «место для скриншота» inside the report, never fabricate output, and never treat an empty frame as evidence.
- Prevent orphan layouts: a heading stays with the following paragraph; a paragraph that introduces a table, figure, or listing stays with its caption/object; a caption never remains alone at a page bottom. A continued native table repeats its header automatically and never splits a row.
- Keep only a short lead-in (at most about 180 characters) with the following figure, table, or listing. Do not bind a long explanatory paragraph to an object when that would leave a large blank area on the preceding page. Do not insert an empty spacer paragraph after a table; use explicit object spacing instead.
- Materialized contents must use hierarchical left indents measured from the left text boundary: level 1 (`TOC 1`) — 0 cm, level 2 (`TOC 2`) — 1.25 cm, level 3 (`TOC 3`) — 2.50 cm. Set the first-line indent to 0 cm at every TOC level; do not add tabs or spaces to imitate hierarchy. Use one right tab stop with dot leader at 16.5 cm, show a page number on every entry, and use 1.5 line spacing. Inspect the rendered contents instead of assuming the TOC field is current.
- The finalizer must write positive cached page numbers measured from the final render and set `updateFields=false` after materialization. This prevents Word from replacing correct cached results with temporary zeroes on open. A zero in any TOC entry is a validation error; after later manual editing the user may deliberately update the field.
- Body prose is always justified (по ширине); the builder rejects `align: left` on ordinary paragraphs. When justified technical prose creates visibly stretched spaces around long identifiers, rewrite or split the paragraph into shorter factual sentences; never leave typographic “rivers” and never switch body prose to left alignment.
- In the default strict-GOST mode, do not silently follow a conflicting assignment or template. Report the exact conflict before building and request a decision when it changes the document materially.

## Final handoff

Return the DOCX path and briefly state:

- which input files were used;
- where the completed laboratory project is located and which required commands passed, when the laboratory was executed;
- which calculations were performed;
- which assumptions remain;
- whether visual render QA passed;
- whether Word must refresh the table of contents on opening.

Do not deliver intermediate JSON, rendered pages, or PDFs unless explicitly requested. Do not leave task-created draft DOCX files, trial PDFs, page renders, cached contents data, validation files, or disposable logs beside the final report after successful delivery. Cleanup is part of completion, not an optional courtesy.
