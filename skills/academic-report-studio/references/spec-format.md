# JSON-спецификация DOCX

## Верхний уровень

```json
{
  "report_type": "lab",
  "language": "ru",
  "profile_path": "/absolute/path/.report-profile.json",
  "subject_profile_path": "/absolute/path/.report-subjects.json",
  "metadata": {},
  "content": [],
  "document": {}
}
```

`report_type`: `lab` или `course`.

`profile_path` необязателен. Если указан, сборщик сначала загружает повторно используемые реквизиты из профиля, затем переопределяет их непустыми значениями из `metadata` текущей работы. Вместо поля можно передать `--profile /absolute/path/.report-profile.json`.

`subject_profile_path` необязателен. Сборщик выбирает преподавателя по точному названию дисциплины без учёта регистра и внешних кавычек. Вместо поля можно передать `--subjects /absolute/path/.report-subjects.json`.

Файл `assets/report-profile.default.json` содержит только подтверждённую институциональную шапку СПбПУ и город; поля студента и группы в нём пусты. `assets/report-subjects.default.json` пуст и не содержит дисциплину или преподавателя. При отсутствии локальных профилей запросить недостающие сведения у пользователя; преподавателя одной дисциплины запрещено переносить в другую.

## Метаданные

```json
{
  "ministry": "Министерство науки и высшего образования Российской Федерации",
  "organization_type": "Федеральное государственное автономное образовательное учреждение высшего образования",
  "institution": "Санкт-Петербургский политехнический университет Петра Великого",
  "institute": "Институт компьютерных наук и кибербезопасности",
  "department": "Высшая школа кибербезопасности",
  "work_number": "3",
  "title": "Название работы",
  "discipline": "Название дисциплины",
  "variant": "7",
  "student_role": "Выполнил",
  "student_status": "студент",
  "student_group": "Номер группы",
  "student_name": "Фамилия Имя Отчество",
  "student_display_name": "Фамилия И.О.",
  "reviewer_role": "Проверил:",
  "reviewer_position": "доцент",
  "reviewer_name": "Фамилия Имя Отчество",
  "reviewer_display_name": "Фамилия И. О.",
  "city": "Санкт-Петербург",
  "year": "2026"
}
```

Неизвестное необязательное поле оставлять пустой строкой. Не вставлять `TBD`, `TODO` или придуманные значения. Обязательны `title`, `discipline`, `student_name`, `student_group`, `reviewer_name`, `reviewer_position`, `city`, `year`; если их нельзя получить из материалов, `.report-profile.json` и `.report-subjects.json`, запросить у пользователя перед финальной сборкой.

`student_name` и `reviewer_name` хранить полностью. Для титульного листа сборщик автоматически преобразует полные имена в форму `Фамилия И.О.` у студента и `Фамилия И. О.` у руководителя согласно локальному профилю. Поля `student_display_name` и `reviewer_display_name` задавать только когда пользователь явно подтвердил другое сокращение.

Повторно используемые реквизиты можно хранить рядом с проектами в `.report-profile.json`:

```json
{
  "organization_type":"Федеральное государственное автономное образовательное учреждение высшего образования",
  "institution":"Санкт-Петербургский политехнический университет Петра Великого",
  "institute":"Институт компьютерных наук и кибербезопасности",
  "department":"Высшая школа кибербезопасности",
  "student_name":"Фамилия Имя Отчество",
  "student_group":"Номер группы",
  "city":"Санкт-Петербург"
}
```

Общий профиль содержит только постоянные сведения. Не помещать в него `reviewer_role`, `reviewer_position` и `reviewer_name`.

Преподавателей хранить отдельно по дисциплинам в `.report-subjects.json`:

```json
{
  "Название дисциплины": {
    "reviewer_role":"Проверил:",
    "reviewer_position":"доцент",
    "reviewer_name":"Фамилия Имя Отчество"
  }
}
```

При подготовке спецификации применять порядок: общий профиль → профиль дисциплины → непустые реквизиты текущей работы. Профили не должны содержать оценки, результаты лабораторных, датасеты или секреты.

Для лабораторной строка на титульном листе формируется как `Лабораторная работа № N`; для курсовой — `Курсовая работа`. Если вид отчёта не известен, его нужно запросить до сборки. В основной части тип не навязывает универсальную структуру: состав разделов берётся из методички.

## Параметры документа

```json
{
  "include_toc": true,
  "toc_levels": 2,
  "page_number_start": 0,
  "author": "",
  "subject": "Учебный отчёт"
}
```

Для программного отчёта обязательно добавить реестр покрытия листингов:

```json
{
  "code_change": {
    "mode": "refactor",
    "original_sources": ["/absolute/path/original/main.py"],
    "final_sources": ["/absolute/path/refactored/app.py", "/absolute/path/refactored/core.py"],
    "test_sources": ["/absolute/path/refactored/tests/test_core.py"],
    "supporting_sources": ["/absolute/path/extra/demo.cpp"],
    "excluded": ["build/ — сборочный вывод", ".venv/ — зависимости"]
  }
}
```

`mode` принимает `new`, `rewrite`, `refactor`, `modify` или `none`. Для `new`, `rewrite` и `modify` массив `final_sources` непустой. Для `refactor` непусты `original_sources` и `final_sources`. Каждый путь из четырёх массивов исходников должен существовать и ровно один раз встречаться в блоке `code` с `presentation:"appendix"`. `test_sources` и `supporting_sources` заполнять, когда соответствующий код написан или изменён. `excluded` содержит только проверенные причины исключения служебных, сгенерированных, бинарных или неизменённых сторонних файлов. Для непрограммной работы использовать `{"mode":"none"}` либо не задавать поле.

`page_number_start: 0` скрывает номер на титульном листе и показывает 1 на первой странице содержания согласно локальному профилю. Не задавать `1`, если пользователь не потребовал другой схемы.

## Блоки содержимого

### Заголовок

```json
{"type":"heading","level":1,"text":"Цель работы","page_break_before":true}
```

Поле `text` содержит только название без цифр. Сборщик связывает `Heading 1`, `Heading 2` и `Heading 3` с настоящей многоуровневой нумерацией Word и отображает `1.`, `1.1.`, `1.1.1.` автоматически. Спецификация с `1. Цель работы` или другим ручным префиксом отклоняется.

В основном тексте заголовки уровней 1, 2 и 3 используют одинаковую позицию номера — 1,25 см от левой границы набора; подзаголовки не получают дополнительного отступа за уровень. Стили `Heading 1–3` имеют прямые левый и абзацный отступы 0 см; на каждый созданный нумерованный абзац сборщик явно ставит левый отступ 0 см и первую строку 1,25 см, сохраняя настоящую многоуровневую нумерацию Word. Ступенчатые отступы применяются только в содержании: `TOC 1` — 0 см, `TOC 2` — 1,25 см, `TOC 3` — 2,50 см, первая строка каждого уровня — 0 см.

Для ненумерованного структурного заголовка можно указать `"structural":true`; для `Содержание`, `Введение`, `Заключение`, `Выводы`, списка источников и приложений это определяется автоматически. Если конкретная методичка требует нумеровать такой раздел, явно указать `"structural":false`.

Если `page_break_before` не указан, сборщик применяет профиль автоматически:

- `Введение`, `Цель работы` и `Задачи` не получают разрыв между собой и должны совместно поместиться на первой содержательной странице; первый блок после содержания всё равно начинается с новой страницы;
- заголовки первого уровня `Ход работы`, `Дополнительные задания`, `Дополнительное задание`, `Выводы` и `Заключение` начинаются с новой страницы;
- заголовки уровней 2–3 не получают автоматический разрыв.

Явное поле `page_break_before` переопределяет профиль только при подтверждённом требовании текущей методики или пользователя. После такого переопределения обязательно проверить финальную пагинацию.

### Абзац

```json
{"type":"paragraph","text":"Текст абзаца."}
```

Для подтверждённого исключения из основного профиля можно явно задать выравнивание и отступ:

```json
{"type":"paragraph","text":"Для достижения поставленной цели необходимо решить следующие задачи:","align":"center","first_indent_cm":0}
```

`align` принимает `justify`, `center` или `right`. Значение `left` для обычного текста запрещено: основной текст всегда выравнивается по ширине. Не задавать эти поля обычным абзацам: они наследуют выравнивание по ширине и отступ 1,25 см. Если из-за длинных идентификаторов появляются растянутые пробелы, переписать абзац более короткими предложениями, а не менять выравнивание.

Для выделения начала:

```json
{"type":"paragraph","bold_prefix":"Цель работы — ","text":"описание цели."}
```

### Список

```json
{"type":"bullet_list","items":["Первый пункт","Второй пункт"]}
```

или:

```json
{"type":"numbered_list","items":["Первый шаг","Второй шаг"]}
```

### Рисунок

```json
{
  "type":"figure",
  "path":"/absolute/path/chart.png",
  "caption":"Результаты эксперимента",
  "number":1,
  "width_cm":14.5,
  "alt_text":"График результатов эксперимента"
}
```

Сборщик располагает абзац изображения по центру с интервалами 0 pt перед/после. Подпись печатается с интервалом 1,5 и интервалами 0 pt перед/после; изображение удерживается с подписью. Пустые абзацы между изображением, подписью и последующим текстом запрещены. Каждая подпись получает стабильную внутреннюю закладку. Ссылка в основном тексте вида `рисунок 2`, `рис. 2` или `на рисунке А.1` автоматически становится чёрной гиперссылкой без подчёркивания, ведущей к подписи. При диапазоне `рисунки А.1–А.4` ссылка ведёт к первому рисунку диапазона.

Если рисунок является алгоритмической блок-схемой, до его создания полностью применить `references/flowcharts.md`. Блок `figure` не исправляет неверную семантику символов, смещённый или выходящий за контур текст, неправильные стрелки, пересечения и ошибочные межстраничные переносы. Эти свойства проверять в исходном изображении и повторно на финальной странице DOCX при масштабе 100 %.

### Таблица

```json
{
  "type":"table",
  "caption":"Результаты измерений",
  "number":1,
  "headers":["Параметр","Значение","Единица"],
  "rows":[["Время","12,4","с"]],
  "widths_cm":[7.0,4.0,3.0],
  "column_alignments":["left","center","right"],
  "line_spacing":1.5,
  "font_family":"Times New Roman",
  "long_token_mode":false,
  "use_final_label":false
}
```

Сумма ширин не должна превышать 16,5 см.

`column_alignments` необязателен. Если задан, число элементов совпадает с числом столбцов; допустимы `left`, `center`, `right`. Шапка всегда центрируется, а массив управляет ячейками данных. Для категорий обычно использовать `left`, для коротких статусов — `center`, для чисел одного формата — согласованное `right` или `center`.

`font_size` необязателен и для отчётной таблицы всегда равен 14 пт. Длинные значения не разрешают уменьшать табличный кегль: меняются структура колонок и ориентация секции.

`line_spacing` для отчётной таблицы всегда равен `1.5`, включая режим длинных токенов.

`font_family` для отчётной таблицы всегда равен `Times New Roman`. Courier New предназначен для листингов кода и не используется для числовых таблиц.

`long_token_mode`, `no_wrap_columns` и альбомные секции в строгом профиле запрещены. Длинное точное значение переносится средствами Word внутри ячейки без изменения текста; таблица сохраняет Times New Roman 14 pt и интервал 1,5.

Слова шапки нельзя разбивать на буквы или слоги. Если заголовок не помещается, расширить колонку, сократить заголовок без потери смысла или разделить таблицу.

`keep_together` для целой таблицы запрещён: он создаёт неоправданные пустые области. Подпись удерживается с первой строкой, остальные строки Word переносит автоматически.

После таблицы сборщик не создаёт пустой абзац-разделитель. Интервал до следующего рисунка, заголовка или абзаца задаётся стилем следующего объекта.

Полная подпись размещается над таблицей по центру. Таблица имеет белый фон, тонкие чёрные границы, Times New Roman 14 pt и полужирную шапку без заливки. При автоматическом продолжении Word повторяет шапку; отдельную надпись продолжения не добавлять.

`rows_per_page` и `use_final_label` в строгом профиле не задавать. Одна логическая таблица остаётся одним объектом DOCX; первая строка получает `w:tblHeader`, каждая строка — `w:cantSplit`.

Номер может быть целым (`1`), номером раздела (`2.1`) или номером приложения (`А.1`). Одну схему применять последовательно ко всем объектам данного типа.

### Формула

```json
{"type":"equation","latex":"\\bar{x}=\\frac{1}{n}\\sum_{i=1}^{n}x_i","number":"1"}
```

Поле `latex` обязательно и содержит одно корректное математическое выражение без внешних разделителей `$`. Сборщик преобразует LaTeX через Pandoc в настоящий редактируемый объект Microsoft Word Equation (`m:oMath`/OMML). Поле `text` для формул устарело и запрещено: оно создавало стилизованный обычный текст и не поддерживало структурные индексы, дроби и операторы.

Для цепочки преобразований использовать выровненный многострочный LaTeX-блок, например `\\begin{aligned}r_{i+1}&=r_{i-1}-q_i r_i\\\\x_{i+1}&=x_{i-1}-q_i x_i\\end{aligned}`. Абзац формулы получает интервал 1,5 и 0 pt до/после. Если выражение слишком длинное, делить его только на смысловой границе согласно `references/formulas-and-pagination.md`. После сборки обязательно проверить наличие OMML структурно и формулу визуально.

### Код

Короткий фрагмент в рамке с обязательной подписью сверху:

```json
{"type":"code","presentation":"fragment","number":1,"caption":"Проверка граничного случая","text":"assert(value == expected);","font_size":12}
```

Полный листинг из реального файла в приложении, без рамки:

```json
{"type":"code","presentation":"appendix","source":"/absolute/path/main.py","label":"src/main.py"}
```

Размер короткого кода — Courier New 12 pt; 11 pt допустим после проверки рендера. Полные листинги размещать после блока `appendix_heading` и печатать Courier New 10 pt, одинарно. Для каждого файла обязательно задавать `label` как безопасный относительный путь без имени домашнего каталога; сборщик выводит его строкой `Файл: …` перед кодом.

### Пустая область под снимок экрана

Когда реальный снимок ещё не передан, разрешён только явно обозначенный блок для будущей вставки:

```json
{"type":"figure_placeholder","number":2,"caption":"Результат выполнения тестов C++","width_cm":15.5,"height_cm":6.0}
```

Перед блоком должна быть естественная ссылка на рисунок. Внутри пустой области нельзя печатать редакторские подсказки, просьбы вставить изображение или иной служебный текст. Не описывать этот блок как полученное доказательство и не заменять им реальный результат запуска.

### Приложение

```json
{"type":"appendix_heading","letter":"А","title":"Листинг программы main.py"}
```

### Разрыв страницы

```json
{"type":"page_break"}
```

### Список источников

Этот блок разрешён и обязателен только при `report_type: "course"`. При `report_type: "lab"` блок `bibliography`, внешние гиперссылки и ссылки `[N]` запрещены.

```json
{
  "type":"bibliography",
  "title":"Список использованных источников",
  "items":[
    {
      "kind":"book",
      "citation":"Stroustrup B. The C++ Programming Language. 4th ed. Addison-Wesley, 2013. ISBN 978-0321563842",
      "url":"https://www.stroustrup.com/4th.html",
      "accessed":"01.08.2026",
      "verified":true
    }
  ]
}
```

`kind` принимает только `book`, `article`, `conference_paper`, `standard`, `official_documentation`, `official_web_resource` или `dataset`. Каждый источник должен быть реально открыт и проверен до сборки; `verified:true` нельзя ставить по названию из поисковой выдачи. `url` — прямой публичный HTTPS-адрес DOI, издателя, журнала, официальной документации, каталога стандарта, учреждения или набора данных. Поисковые страницы, локальные пути, задание лабораторной, методический PDF текущей работы, код проекта, скриншоты, чужие отчёты и ответы ИИ в список не включать.

Для курсовой блок `bibliography` обязателен и содержит минимум один проверенный источник.

Внешняя гиперссылка создаётся только для `url` библиографического элемента и должна вести непосредственно к проверенной статье, DOI, странице издателя, стандарту или официальному ресурсу. Ссылка `[N]` в тексте курсовой автоматически превращается во внутреннюю гиперссылку на пункт N и должна соответствовать существующему элементу. Внутренние ссылки содержания и рисунков разрешены для обоих типов. Дату обращения задавать как `ДД.ММ.ГГГГ`.

## Минимальный пример

```json
{
  "report_type":"lab",
  "metadata":{
    "title":"Исследование алгоритма",
    "discipline":"Название дисциплины",
    "institution":"Санкт-Петербургский политехнический университет Петра Великого",
    "institute":"Институт компьютерных наук и кибербезопасности",
    "department":"Высшая школа кибербезопасности",
    "student_group":"Номер группы",
    "student_name":"Фамилия Имя Отчество",
    "reviewer_position":"доцент",
    "reviewer_name":"Фамилия Имя Отчество",
    "city":"Санкт-Петербург",
    "year":"2026"
  },
  "document":{"include_toc":true},
  "content":[
    {"type":"heading","level":1,"text":"Цель работы","page_break_before":true},
    {"type":"paragraph","bold_prefix":"Цель работы — ","text":"исследовать алгоритм."},
    {"type":"heading","level":1,"text":"Ход работы","page_break_before":true},
```
