# JSON-спецификация DOCX

## Верхний уровень

```json
{
  "report_type": "lab",
  "language": "ru",
  "profile_path": "/absolute/path/.report-profile.json",
  "subject_profile_path": "/absolute/path/.report-subjects.json",
  "metadata": {},
  "content": [],
  "document": {}
}
```

`report_type`: `lab` или `course`.

`profile_path` необязателен. Если указан, сборщик сначала загружает повторно используемые реквизиты из профиля, затем переопределяет их непустыми значениями из `metadata` текущей работы. Вместо поля можно передать `--profile /absolute/path/.report-profile.json`.

`subject_profile_path` необязателен. Сборщик выбирает преподавателя по точному названию дисциплины без учёта регистра и внешних кавычек. Вместо поля можно передать `--subjects /absolute/path/.report-subjects.json`.

Файл `assets/report-profile.default.json` содержит только подтверждённую институциональную шапку СПбПУ и город; поля студента и группы в нём пусты. `assets/report-subjects.default.json` пуст и не содержит дисциплину или преподавателя. При отсутствии локальных профилей запросить недостающие сведения у пользователя; преподавателя одной дисциплины запрещено переносить в другую.

## Метаданные

```json
{
  "ministry": "Министерство науки и высшего образования Российской Федерации",
  "organization_type": "Федеральное государственное автономное образовательное учреждение высшего образования",
  "institution": "Санкт-Петербургский политехнический университет Петра Великого",
  "institute": "Институт компьютерных наук и кибербезопасности",
  "department": "Высшая школа кибербезопасности",
  "work_number": "3",
  "title": "Название работы",
  "discipline": "Название дисциплины",
  "variant": "7",
  "student_role": "Выполнил",
  "student_status": "студент",
  "student_group": "Номер группы",
  "student_name": "Фамилия Имя Отчество",
  "student_display_name": "Фамилия И.О.",
  "reviewer_role": "Проверил:",
  "reviewer_position": "доцент",
  "reviewer_name": "Фамилия Имя Отчество",
  "reviewer_display_name": "Фамилия И. О.",
  "city": "Санкт-Петербург",
  "year": "2026"
}
```

Неизвестное необязательное поле оставлять пустой строкой. Не вставлять `TBD`, `TODO` или придуманные значения. Обязательный набор зависит от титульного макета `cover_layout`:

- `lab` и `course` (по умолчанию): `title`, `discipline`, `student_name`, `student_group`, `reviewer_name`, `reviewer_position`, `city`, `year`;
- `vkr_2026` и `vkr_tr23`: `title`, `student_name`, `student_group`, `city`, `year`; поля `advisor_name`, `advisor_position`, `student_course`, `direction`, `profile_name`, `approver_name`, `approver_position` заполняются при наличии, иначе остаются форменными прочерками;
- `nir`: `title`, `city`, `year`; поля `udc`, `reg_nioktr`, `reg_ikrbs`, `short_name`, `report_stage`, `leader_name`, `leader_position`, `approver_name`, `approver_position` заполняются при наличии.

Если обязательные поля нельзя получить из материалов, `.report-profile.json` и `.report-subjects.json`, запросить у пользователя перед финальной сборкой. Институт и высшая школа по умолчанию — ИКНК и ВШК из `assets/report-profile.default.json`; подставлять только подтверждённые значения.

`student_name` и `reviewer_name` хранить полностью. Для титульного листа сборщик автоматически преобразует полные имена в форму `Фамилия И.О.` у студента и `Фамилия И. О.` у руководителя согласно локальному профилю. Поля `student_display_name` и `reviewer_display_name` задавать только когда пользователь явно подтвердил другое сокращение.

Повторно используемые реквизиты можно хранить рядом с проектами в `.report-profile.json`:

```json
{
  "organization_type":"Федеральное государственное автономное образовательное учреждение высшего образования",
  "institution":"Санкт-Петербургский политехнический университет Петра Великого",
  "institute":"Институт компьютерных наук и кибербезопасности",
  "department":"Высшая школа кибербезопасности",
  "student_name":"Фамилия Имя Отчество",
  "student_group":"Номер группы",
  "city":"Санкт-Петербург"
}
```

Общий профиль содержит только постоянные сведения. Не помещать в него `reviewer_role`, `reviewer_position` и `reviewer_name`.

Преподавателей хранить отдельно по дисциплинам в `.report-subjects.json`:

```json
{
  "Название дисциплины": {
    "reviewer_role":"Проверил:",
    "reviewer_position":"доцент",
    "reviewer_name":"Фамилия Имя Отчество"
  }
}
```

При подготовке спецификации применять порядок: общий профиль → профиль дисциплины → непустые реквизиты текущей работы. Профили не должны содержать оценки, результаты лабораторных, датасеты или секреты.

Для лабораторной строка на титульном листе формируется как `Лабораторная работа № N`; для курсовой — `Курсовая работа`. Если вид отчёта не известен, его нужно запросить до сборки. В основной части тип не навязывает универсальную структуру: состав разделов берётся из методички.

## Параметры документа

```json
{
  "include_toc": true,
  "toc_levels": 2,
  "format_profile": "unified",
  "page_number_start": 1,
  "author": "",
  "subject": "Учебный отчёт"
}
```

`format_profile` принимает `unified` — единый профиль тела (ГОСТ 7.32-2017 +
tr23-26), одинаковый для лабораторной, курсовой, ВКР и отчёта о НИР. Исторические
значения `spbpu` и `student_default` принимаются и отображаются на `unified`:
тел документа больше не различаются, вид работы меняет только титульный лист
(`metadata.cover_layout`, см. `references/layout-profile.md`).

Сборщик автоматически применяет поля 30/15/20/20 мм, номера заголовков без
завершающей точки, прописные структурные заголовки, разрыв страницы у каждого
раздела основной части, левое выравнивание названия таблицы, табличный текст
12 пт с одинарным интервалом, одинарные подписи, зазоры «одной пустой строки»
(21 пт) вокруг заголовков подразделов, рисунков, таблиц и формул, тире в
перечислениях, автоматические переносы и сквозной счёт страниц от титульного
листа. Вид работы меняет только титульный лист и набор структурных элементов.

Для программного отчёта обязательно добавить реестр покрытия листингов:

```json
{
  "code_change": {
    "mode": "refactor",
    "original_sources": ["/absolute/path/original/main.py"],
    "final_sources": ["/absolute/path/refactored/app.py", "/absolute/path/refactored/core.py"],
    "test_sources": ["/absolute/path/refactored/tests/test_core.py"],
    "supporting_sources": ["/absolute/path/extra/demo.cpp"],
    "excluded": ["build/ — сборочный вывод", ".venv/ — зависимости"]
  }
}
```

`mode` принимает `new`, `rewrite`, `refactor`, `modify` или `none`. Для `new`, `rewrite` и `modify` массив `final_sources` непустой. Для `refactor` непусты `original_sources` и `final_sources`. Каждый путь из четырёх массивов исходников должен существовать и ровно один раз встречаться в блоке `code` с `presentation:"appendix"`. `test_sources` и `supporting_sources` заполнять, когда соответствующий код написан или изменён. `excluded` содержит только проверенные причины исключения служебных, сгенерированных, бинарных или неизменённых сторонних файлов. Для непрограммной работы использовать `{"mode":"none"}` либо не задавать поле.

Значение по умолчанию `page_number_start: 1`: сквозной счёт от титульного
листа, номер на нём скрыт. Первый видимый номер равен физическому номеру
страницы в рендере (содержание может начинаться с 2 и более после задания,
реферата и перечня сокращений) и не хардкодится. Явное другое значение
использовать только при подтверждённом требовании методички.

## Блоки содержимого

### Заголовок

```json
{"type":"heading","level":1,"text":"Цель работы","page_break_before":true}
```

Поле `text` содержит только название без цифр. Сборщик связывает `Heading 1`, `Heading 2` и `Heading 3` с настоящей многоуровневой нумерацией Word и отображает `1`, `1.1`, `1.1.1` — без конечной точки (tr23-26 3.5.1). Спецификация с `1. Цель работы` или другим ручным префиксом отклоняется.

В основном тексте заголовки уровней 1, 2 и 3 используют одинаковую позицию номера — 1,25 см от левой границы набора; подзаголовки не получают дополнительного отступа за уровень. Стили `Heading 1–3` имеют прямые левый и абзацный отступы 0 см; на каждый созданный нумерованный абзац сборщик явно ставит левый отступ 0 см и первую строку 1,25 см, сохраняя настоящую многоуровневую нумерацию Word. Ступенчатые отступы применяются только в содержании: `TOC 1` — 0 см, `TOC 2` — 0,5 см, `TOC 3` — 1,0 см (tr23-26 2.5.1), первая строка каждого уровня — 0 см.

Для ненумерованного структурного заголовка можно указать `"structural":true`; для `Содержание`, `Введение`, `Заключение`, `Выводы`, списка источников и приложений это определяется автоматически. Если конкретная методичка требует нумеровать такой раздел, явно указать `"structural":false`.

Если `page_break_before` не указан, сборщик применяет профиль автоматически:

- каждый структурный элемент и КАЖДЫЙ раздел основной части (уровень 1) начинается с новой страницы (ГОСТ 7.32-2017 6.2.1, tr23-26 3.3.1);
- заголовки уровней 2–3 продолжаются в потоке и получают зазор 21 пт сверху — эквивалент одной свободной строки (tr23-26 3.3.3).

Явное поле `page_break_before` переопределяет профиль только при подтверждённом требовании текущей методики или пользователя. После такого переопределения обязательно проверить финальную пагинацию.

### Абзац

```json
{"type":"paragraph","text":"Текст абзаца."}
```

Для подтверждённого исключения из основного профиля можно явно задать выравнивание и отступ:

```json
{"type":"paragraph","text":"Для достижения поставленной цели необходимо решить следующие задачи:","align":"center","first_indent_cm":0}
```

`align` принимает `justify`, `center` или `right`. Значение `left` для обычного текста запрещено: основной текст всегда выравнивается по ширине. Не задавать эти поля обычным абзацам: они наследуют выравнивание по ширине и отступ 1,25 см. Если из-за длинных идентификаторов появляются растянутые пробелы, переписать абзац более короткими предложениями, а не менять выравнивание.

Для выделения начала:

```json
{"type":"paragraph","bold_prefix":"Цель работы – ","text":"описание цели."}
```

Любая формула внутри строки текста, элемента списка, примечания или подрисуночной подписи задаётся маркером `$…$` с LaTeX внутри и собирается настоящим inline-OMML (Cambria Math), а не обычными буквами:

```json
{"type":"paragraph","text":"Последняя строка проходит проверку равенством $d = xa + yb$."}
```

Маркер применим только к коротким выражениям без переносов и окружений; выносные формулы по-прежнему оформляются блоком `equation`. Любое выражение с операциями (`·`, `×`, `/`, `=`) в прозе обязано быть маркером `$…$`: текстовые псевдоформулы вида `k·ab/d` или `d = xa + yb` запрещены и отклоняются валидатором. Исключение — русские обозначения единиц (`м/с`, `Н·м`), формулами не являющиеся.

### Список

```json
{"type":"bullet_list","items":["Первый пункт","Второй пункт"]}
```

или:

```json
{"type":"numbered_list","items":["Первый шаг","Второй шаг"]}
```

В едином профиле обычное перечисление оформлять тире (Word-нумерация `List Number` использует метку `1)`). Для элементов,
на которые нужны ссылки, использовать русские строчные буквы со скобкой; для
вложенного уровня — арабские цифры со скобкой. Не подменять эти уровни маркером
`•`. Пунктуацию согласовать с вводной фразой по
`references/spbpu-profile.md`.

### Примечание

Одно примечание:

```json
{"type":"note","text":"Пояснение к предыдущему объекту."}
```

Несколько примечаний:

```json
{"type":"note","items":["Первое пояснение.","Второе пояснение."]}
```

Блок ставить непосредственно после связанного текста, таблицы или рисунка.

Настоящая сноска Word создаётся маркером `[^текст сноски]` внутри абзаца,
элемента списка или примечания:

```json
{"type":"paragraph","text":"Значения получены стендовым измерением[^измерения выполнены на стенде № 2]."}
```

Сборщик превращает маркер в надстрочный номер и настоящую запись
`word/footnotes.xml` внизу страницы с разделительной линией (tr23-26 3.8.5).
Имитировать сноску обычным абзацем запрещено.

### Перечень сокращений

```json
{
  "type":"abbreviations",
  "items":[
    {"term":"АСУ","definition":"автоматизированная система управления"},
    {"term":"МК","definition":"микроконтроллер"}
  ]
}
```

Перечень составляют только при более чем трёх обозначениях (tr23-26 2.4.2);
иначе раскрывать каждое сокращение при первом употреблении в тексте. Сборщик
сортирует пункты по алфавиту и печатает вводную фразу «В настоящей работе
применяют следующие сокращения и обозначения:»; расшифровка идёт через тире.
Блок автоматически размещается перед содержанием; `"position":"body"`
оставляет его в основном потоке.

### Реферат (ВКР и отчёт о НИР)

```json
{
  "type":"abstract",
  "keywords":["СЕТЕВОЙ ТРАФИК","АНАЛИЗ","ПАКЕТЫ","ПРОТОКОЛ","БЕЗОПАСНОСТЬ"],
  "text":["Работа посвящена…","Проведено тестирование…"],
  "en":{"keywords":["NETWORK TRAFFIC","ANALYSIS","PACKETS","PROTOCOL","SECURITY"],
        "text":["The work is devoted to…","The package was tested…"]}
}
```

Сборщик печатает страницу РЕФЕРАТ со строкой объёма «Работа содержит: __ с.,
N рис., N табл., N источников, N прил.» — числа объектов считает по спеке,
число страниц заполняет `finalize_toc.py` по факту рендера; далее ключевые
слова (5–15, прописными, tr23-26 2.3.2) и текст. Затем печатает страницу
ABSTRACT — английскую версию (tr23-26 2.3.4). Блок автоматически размещается
перед содержанием.

### Задание (ВКР, только если вшивается по требованию методички)

```json
{
  "type":"assignment",
  "fields":[
    {"label":"Тема работы","value":"Разработка программного комплекса"},
    {"label":"Срок сдачи","value":""},
    {"label":"Исходные данные по работе","value":""}
  ]
}
```

Печатает страницу ЗАДАНИЕ с нумерованными полями; пустое значение остаётся
форменным прочерком. По примечанию к Приложению Б tr23-26 задание не вшивается
в ВКР — включать блок только по явному требованию методички или пользователя.

### Рисунок

```json
{
  "type":"figure",
  "path":"/absolute/path/chart.png",
  "caption":"Результаты эксперимента",
  "number":1,
  "width_cm":14.5,
  "alt_text":"График результатов эксперимента",
  "annotation":["1 – датчик; 2 – усилитель"]
}
```

Необязательное поле `annotation` добавляет пояснительные данные между изображением и подписью (tr23-26 3.6.7):

```json
{"type":"figure","path":"…","caption":"Кинематическая схема стенда","number":1,
 "annotation":["1 – пневматическая камера; 2 – кран; 3 – концевая гайка штока"]}
```

Сборщик располагает абзац изображения по центру с зазором 21 пт сверху
(эквивалент одной свободной строки, tr23-26 3.6.6); зазор после подписи
сборщик ставит следующему текстовому абзацу. Подпись печатается с одинарным
интервалом и интервалами 0 pt перед/после; изображение, пояснительные данные
и подпись удерживаются вместе. Пустые абзацы между изображением, подписью
и последующим текстом запрещены. Каждая подпись получает стабильную внутреннюю закладку. Ссылка в основном тексте вида `рисунок 2`, `рис. 2` или `на рисунке А.1` автоматически становится чёрной гиперссылкой без подчёркивания, ведущей к подписи. При диапазоне `рисунки А.1–А.4` ссылка ведёт к первому рисунку диапазона.

Если рисунок является алгоритмической блок-схемой, до его создания полностью применить `references/flowcharts.md`. Блок `figure` не исправляет неверную семантику символов, смещённый или выходящий за контур текст, неправильные стрелки, пересечения и ошибочные межстраничные переносы. Эти свойства проверять в исходном изображении и повторно на финальной странице DOCX при масштабе 100 %.

### Таблица

```json
{
  "type":"table",
  "caption":"Результаты измерений",
  "number":1,
  "headers":["Параметр","Значение","Единица"],
  "rows":[["Время","12,4","с"]],
  "widths_cm":[7.0,4.0,3.0],
  "column_alignments":["left","center","right"],
  "font_family":"Times New Roman",
  "long_token_mode":false,
  "use_final_label":false
}
```

Сумма ширин не должна превышать полезную ширину 16,5 см (поля 30/15/20/20 мм).

`column_alignments` необязателен. Если задан, число элементов совпадает с числом столбцов; допустимы `left`, `center`, `right`. Шапка всегда центрируется, а массив управляет ячейками данных. Для категорий обычно использовать `left`, для коротких статусов — `center`, для чисел одного формата — согласованное `right` или `center`.

`font_size` и `line_spacing` обычно не задавать: единый профиль использует
Times New Roman 12 пт с одинарным интервалом (tr23-26 3.7.11).

`font_family` для отчётной таблицы всегда равен `Times New Roman`. Courier New предназначен для листингов кода и не используется для числовых таблиц.

`long_token_mode` и `no_wrap_columns` запрещены. Длинное точное значение
переносится средствами Word внутри ячейки без изменения текста.

Слова шапки нельзя разбивать на буквы или слоги. Если заголовок не помещается, расширить колонку, сократить заголовок без потери смысла или разделить таблицу.

`keep_together` для целой таблицы запрещён: он создаёт неоправданные пустые области. Подпись удерживается с первой строкой, остальные строки Word переносит автоматически.

Полная подпись размещается над таблицей слева без абзацного отступа
(tr23-26 3.7.1); таблица использует Times New Roman 12 пт и одинарный интервал;
первая подпись получает зазор 21 пт сверху. После таблицы сборщик не создаёт
пустой абзац-разделитель: зазор задаётся на следующем абзаце.

После пробного рендера можно задать фактическое число строк одной физической
части через `rows_per_page`: сборщик создаст части на новых страницах с
надписями `Продолжение таблицы N` над каждой частью, включая последнюю
(tr23-26 3.7.7). `use_final_label` запрещён: пособие требует слово
`Продолжение` над всеми продолжающими частями. Не угадывать значение до
рендера.

Номер может быть целым (`1`), номером раздела (`2.1`) или номером приложения (`А.1`). Одну схему применять последовательно ко всем объектам данного типа.

### Формула

```json
{"type":"equation","latex":"\\bar{x}=\\frac{1}{n}\\sum_{i=1}^{n}x_i","number":"1"}
```

Поле `latex` обязательно и содержит одно корректное математическое выражение без внешних разделителей `$`. Сборщик преобразует LaTeX через Pandoc в настоящий редактируемый объект Microsoft Word Equation (`m:oMath`/OMML). Поле `text` для формул устарело и запрещено: оно создавало стилизованный обычный текст и не поддерживало структурные индексы, дроби и операторы.

Для цепочки преобразований создавать отдельный блок `equation` на каждый шаг: выровненные многострочные блоки `aligned`, матрицы равенств и equation array запрещены (см. `references/formulas-and-pagination.md`). Абзац формулы получает интервал 1,5, зазор 21 пт сверху — эквивалент одной свободной строки по ГОСТ 7.32-2017 6.8.1 — и 0 pt после; зазор после формулы сборщик ставит следующему абзацу. Номер `(N)` задаётся только для формул, на которые есть ссылка в тексте (tr23-26 3.9.3). Если выражение слишком длинное, делить его только на смысловой границе. После сборки обязательно проверить наличие OMML структурно и формулу визуально.

### Код

Короткий фрагмент в рамке с обязательной подписью сверху:

```json
{"type":"code","presentation":"fragment","number":1,"caption":"Проверка граничного случая","text":"assert(value == expected);","font_size":12}
```

Полный листинг из реального файла в приложении, без рамки:

```json
{"type":"code","presentation":"appendix","source":"/absolute/path/main.py","label":"src/main.py"}
```

Размер короткого кода — Courier New 12 pt; 11 pt допустим после проверки рендера. Полные листинги размещать после блока `appendix_heading` и печатать Courier New 10 pt, одинарно. Для каждого файла обязательно задавать `label` как безопасный относительный путь без имени домашнего каталога; сборщик выводит его строкой `Файл: …` перед кодом.

### Пустая область под снимок экрана

Когда реальный снимок ещё не передан, разрешён только явно обозначенный блок для будущей вставки:

```json
{"type":"figure_placeholder","number":2,"caption":"Результат выполнения тестов C++","width_cm":15.5,"height_cm":6.0}
```

Перед блоком должна быть естественная ссылка на рисунок. Внутри пустой области нельзя печатать редакторские подсказки, просьбы вставить изображение или иной служебный текст. Не описывать этот блок как полученное доказательство и не заменять им реальный результат запуска.

### Приложение

```json
{"type":"appendix_heading","letter":"А","title":"Листинг программы main.py"}
```

### Разрыв страницы

```json
{"type":"page_break"}
```

### Список источников

Этот блок разрешён и обязателен для курсовой, ВКР и отчёта о НИР (`report_type: "course"` с любым `cover_layout`, кроме `lab`). При `cover_layout: "lab"` блок `bibliography`, внешние гиперссылки и ссылки `[N]` запрещены.

```json
{
  "type":"bibliography",
  "title":"Список использованных источников",
  "items":[
    {
      "kind":"book",
      "citation":"Stroustrup B. The C++ Programming Language. 4th ed. Addison-Wesley, 2013. ISBN 978-0321563842",
      "url":"https://www.stroustrup.com/4th.html",
      "accessed":"01.08.2026",
      "verified":true
    }
  ]
}
```

`kind` принимает только `book`, `article`, `conference_paper`, `standard`, `official_documentation`, `official_web_resource` или `dataset`. Каждый источник должен быть реально открыт и проверен до сборки; `verified:true` нельзя ставить по названию из поисковой выдачи. `url` — прямой публичный HTTPS-адрес DOI, издателя, журнала, официальной документации, каталога стандарта, учреждения или набора данных. Поисковые страницы, локальные пути, задание лабораторной, методический PDF текущей работы, код проекта, скриншоты, чужие отчёты и ответы ИИ в список не включать.

Для курсовой блок `bibliography` обязателен и содержит минимум один проверенный источник.

Внешняя гиперссылка создаётся только для `url` библиографического элемента и должна вести непосредственно к проверенной статье, DOI, странице издателя, стандарту или официальному ресурсу. Ссылка `[N]` в тексте курсовой автоматически превращается во внутреннюю гиперссылку на пункт N и должна соответствовать существующему элементу. Внутренние ссылки содержания и рисунков разрешены для обоих типов. Дату обращения задавать как `ДД.ММ.ГГГГ`.
