# Автоматизация отчёта по лабораторной работе

## Минимальный запуск

Для выполнения самой лабораторной и отчёта пользователю достаточно написать:

> Выполни лабораторную строго по методичке и сделай отчёт по ГОСТ. Папка с материалами: `/абсолютный/путь`. Проект и итоговый DOCX сохрани там же.

Фраза `сделай/выполни лабораторную` включает реализацию, расчёты, запуск и тестирование, а не только написание текста. В таком режиме обязательно читать `execute-lab.md`. Если пользователь явно просит только отчёт по уже выполненной работе, не изменять проект и применять режим `report-only`.

Если рядом находится заполненный `.report-profile.json`, повторно не спрашивать ФИО, группу и организацию. Преподавателя и должность брать из `.report-subjects.json` по текущей дисциплине. Из задания извлекать дисциплину, номер, тему и вариант. Если вид отчёта не указан явно и его нельзя однозначно прочитать из задания, сначала спросить, нужен отчёт лабораторной или курсовая работа. Для новой дисциплины одним сообщением запросить ФИО и должность преподавателя, затем предложить сохранить их в предметном профиле.

Скилл автономен относительно старых отчётов: для оформления достаточно встроенного `layout-profile.md`, генератора, валидатора и профилей реквизитов. Старые пользовательские DOCX/PDF можно анализировать только по отдельной просьбе для изменения профиля; их отсутствие не является блокером.

## Запуск на разных платформах

1. Определить Python в порядке: текущий интерпретатор агента; `python3`; `py -3` в Windows; `python`.
2. Проверить импорт зависимостей до сборки. Если их нет, использовать изолированную виртуальную среду проекта; установку из сети согласовать.
3. Все пути передавать аргументами и заключать в кавычки. В JSON хранить корректные абсолютные пути текущей машины только для текущей сборки; в исходном проекте использовать относительные пути.
4. Для рендера использовать bundled `scripts/render_docx.py`, который ищет LibreOffice (`soffice`) в `PATH` и стандартных каталогах Windows/macOS/Linux, затем использует PyMuPDF или `pdftoppm`. Если LibreOffice отсутствует, DOCX можно собрать и структурно проверить, но финальную визуальную проверку считать заблокированной до появления конвертера.
5. Если отчёт содержит блок-схему алгоритма, программы, данных или системы, до генерации полностью прочитать `references/flowcharts.md`. После генерации проверить семантику символов, попадание текста в безопасную область каждого блока, ориентацию наконечников, порты входа/выхода, подписи ветвей, соединители и читаемость на странице DOCX при 100 %.
6. Не требовать Bash, Make, PowerShell или конкретную оболочку, если это не указано методичкой. Выбирать нативную команду проекта и сохранять её в журнале.

## Рекомендуемая папка проекта

Структура необязательна, но ускоряет работу:

```text
lab-03/
├── .report-profile.json
├── .report-subjects.json
├── assignment/      # задание и методичка
├── data/            # CSV, XLSX, JSON и другие датасеты
├── src/             # исходный код и ноутбуки
├── screenshots/     # подтверждающие изображения
├── references/      # разрешённые источники текущей работы
└── output/          # итоговый DOCX
```

Не требовать переименования файлов. Работать и с плоской папкой, определяя роль файла по расширению, имени и содержимому.

## Расположение итогового DOCX

Определять папку сохранения до сборки и применять следующий приоритет:

1. Точный файл или папка назначения, которые явно указал пользователь.
2. Папка, в которой лежит основная методичка или файл задания текущей работы.
3. Переданная пользователем папка материалов или проекта, если отдельной методички нет.

Если пользователь передал только папку, сначала найти в ней основную методичку и сохранить итоговый DOCX рядом именно с ней, даже когда методичка находится во вложенной папке. Черновики, JSON, PDF, PNG и журналы держать в одном выделенном рабочем каталоге; в папку назначения переносить только проверенный финальный DOCX. После успешной финальной проверки удалить рабочий каталог и отдельные task-created draft DOCX через `scripts/cleanup_report_work.py --apply`. Не удалять входные материалы, проект, профили, финальный DOCX и доказательства, которые методичка требует сдавать отдельно. Если запись в выбранную папку требует разрешения, запросить его, а не сохранять итог незаметно в другом месте. Не оставлять единственный финальный экземпляр во временной папке или каталоге рендера.

## Конвейер

1. Инвентаризация:
   - перечислить все файлы, типы, размеры, листы/столбцы датасетов, число страниц и доступность чтения;
   - отделить задание и методичку от исходных данных, реализации и результатов;
   - исключить временные файлы Word, кэш, секреты и прежние результаты сборки.
2. Реквизиты:
   - объединить постоянный `.report-profile.json`, преподавателя из `.report-subjects.json` и текущее задание;
   - не переносить преподавателя между разными дисциплинами;
   - текущие непустые данные имеют приоритет;
   - проверить написание ФИО, группу, должность преподавателя, дисциплину, номер, тему, вариант, город и год.
3. Декомпозиция задания:
   - выписать каждый обязательный пункт, требуемый результат, формулу, таблицу, рисунок, листинг и контрольный вопрос;
   - сформировать внутреннюю матрицу трассировки без включения её в отчёт, если она не нужна пользователю.
   - для программной работы сформировать реестр исходников: режим изменения (`new`, `rewrite`, `refactor`, `modify`), исходные файлы до изменений, итоговые файлы, тесты, дополнительные программные эксперименты и обоснованно исключённые служебные/сторонние файлы;
4. Выполнение лабораторной, если выбран режим `execute-and-report`:
   - превратить каждый пункт методички в проверяемый критерий;
   - реализовать обязательную часть и выбранный вариант;
   - использовать точные имена, ограничения и инструментальную цепочку из задания;
   - запустить сборку, контрольные примеры, обязательные и граничные тесты;
   - дополнительные задания выполнять только по прямому указанию;
   - перейти к отчёту только после execution gate из `execute-lab.md`.
5. Воспроизводимое выполнение:
   - изучить код до запуска;
   - не запускать неизвестные скрипты, способные изменить внешние системы или удалить данные;
   - для безопасных локальных расчётов фиксировать команду, версию среды, параметры, seed, входы и выходы;
   - проверять числовые результаты независимым пересчётом, когда это разумно;
   - не выдавать предоставленный скриншот или старый лог за результат нового запуска.
6. Подготовка материалов:
   - строить таблицы из проверенных данных, сохранять единицы и правила округления;
   - строить читаемые графики без декоративной перегрузки;
   - использовать только скриншоты, подтверждающие конкретный этап; обрезать интерфейс до релевантной области, не скрывая существенный контекст;
   - короткие объясняемые фрагменты оформлять в тонкой рамке с подписью сверху, Courier New 12 pt;
   - длинные листинги переносить в приложения без рамки, Courier New 10 pt;
   - если команда безопасно выполняется, использовать реальный снимок или точное представление её сохранённого вывода; если результата получить нельзя, оставлять пустую подписанную рамку без редакторского текста внутри и не подменять ею доказательства.
7. Черновик:
   - следовать порядку из `structures-and-writing.md` и текущего задания;
   - для каждого пункта писать: что требовалось, как устроена конкретная реализация, почему выбран такой подход, какой результат получен и как он проверен;
   - в программной работе подробно раскрывать структуру данных, владение ресурсами, инварианты, алгоритмы ключевых операций, обработку ошибок, интеграцию компонентов и устройство тестов; не повторять код построчно и не добавлять общие фразы;
   - привязывать текст к конкретному варианту, именам из кода, фактическим командам и результатам, чтобы отчёт не был универсальным шаблоном;
   - использовать естественный сдержанный язык студента без пустых вводных фраз, искусственных ошибок и попыток обхода детекторов;
   - ставить ссылку в тексте перед каждой таблицей и каждым рисунком;
   - выводы связать с целью и фактическими результатами.
   - сформировать обязательные приложения с полными листингами: итоговый код для любой программной работы; исходный и итоговый код для рефакторинга/переписывания; тесты и дополнительные программные эксперименты отдельными приложениями. Перед каждым файлом указать его относительный путь; каталог проекта не считать заменой листинга.
   - не добавлять в лабораторный отчёт список литературы, внешние гиперссылки или ссылки `[N]`; методичку называть заданием без библиографического номера.
8. Сборка и контроль:
   - собрать только DOCX;
   - запустить структурный валидатор;
   - отрендерить и просмотреть все страницы;
   - сверить рендер с `layout-profile.md`: титульную композицию, Times New Roman 14 pt, поля 3/1,5/2/2 см, правую нумерацию, многоуровневые заголовки, рамки кода и содержание;
   - исправить переносы таблиц, висячие заголовки, подписи, нумерацию, обрезанные рисунки, пустые страницы и переполнения;
   - убедиться, что в таблицах нет серой или цветной заливки, а текст и подписи имеют 14 pt;
   - проверить содержание: уровни имеют отступы 0/1,25/2,5 см, каждая строка заканчивается номером страницы, а правый табулятор не выходит за рабочую ширину 16,5 см;
   - проверить, что номера содержания положительные и после материализации `updateFields=false`; значение 0 считать ошибкой;
   - проверить заголовки основной части: номер начинается на 1,25 см от границы набора, а отступ стиля не складывается с отступом нумерации;
   - проверить разрывы основных разделов: `Введение` при его наличии, `Цель работы` и `Задачи` находятся на одной первой содержательной странице; `Ход работы`, `Дополнительные задания` и `Выводы` начинаются каждый с новой страницы; подразделы уровней 2–3 не получают лишних принудительных разрывов;
   - проверить рисунки: абзац изображения 0/0 pt, подпись 1,5 строки и 0/0 pt, подпись не оторвана от изображения;
   - не удерживать длинный вводный абзац вместе с рисунком/таблицей, если это оставляет половину страницы пустой; не добавлять пустой абзац после таблицы;
   - выполнить постраничный аудит плотности: кроме титульного листа, содержания, намеренно изолированной вводной страницы, начала приложения и естественной последней страницы, содержимое не должно систематически заканчиваться выше 60 % полезной высоты; причину каждого исключения зафиксировать и исправить, не добавляя текст-наполнитель;
   - короткие таблицы до 10 строк, помещающиеся на свежей странице, удерживать целиком; длинные таблицы делить только между строками с повторной шапкой и надписью `Продолжение таблицы N`; не оставлять отдельную страницу ради одной строки; не допускать разрыва слов в шапке и чисел/идентификаторов внутри токена, применяя при необходимости режим длинных токенов из `spacing-and-layout-from-examples.md`;
   - сверить приложения с `document.code_change`: каждый исходный, итоговый, тестовый и дополнительный файл присутствует ровно один раз полным листингом; при `refactor` обе версии существуют одновременно; видимые подписи файлов содержат относительные пути;
   - повторять цикл до прохождения проверок.
9. Контроль достоверности:
   - проверить происхождение каждого числа, таблицы, рисунка и вывода по матрице трассировки;
   - не считать наличие файла доказательством его содержимого — открыть и проверить релевантный фрагмент;
   - не описывать запуск программы, если был выполнен только анализ исходного кода;
   - при расхождении между заданием, датасетом и кодом сообщить о нём, не выбирать удобное значение молча;
   - не завершать отчёт, пока обязательный результат имеет статус `missing`.
10. Финальная очистка:
   - проверить, что финальный DOCX существует в папке сдачи, имеет ненулевой размер, прошёл структурную валидацию и постраничный визуальный QA;
   - выполнить сухой запуск `cleanup_report_work.py` и сверить каждый путь;
   - повторить с `--apply`, удалив выделенный рабочий каталог, черновики и пробные рендеры;
   - убедиться, что финальный DOCX, исходный проект и пользовательские материалы сохранены, а disposable PDF/PNG/JSON/log артефакты отсутствуют.

## Матрица трассировки

В рабочем JSON вести для каждого пункта:

```json
{
  "task_item":"Построить график зависимости y(x)",
  "status":"computed",
  "inputs":["data/measurements.csv"],
  "method":"Линейная аппроксимация методом наименьших квадратов",
  "outputs":["work/figure-1.png", "коэффициенты a и b"],
  "report_location":"2.2 Обработка результатов",
  "verification":"повторный расчёт коэффициентов"
}
```

Допустимые статусы: `provided`, `computed`, `observed`, `inferred`, `missing`. Не включать внутреннюю матрицу в итоговый DOCX без просьбы пользователя.

## Правила автозапроса

Сначала перечислить найденные обязательные реквизиты, затем одной короткой группой запросить только пропуски. Не задавать по одному вопросу в нескольких сообщениях. Не начинать финальный титульный лист без:

- вида отчёта — лабораторная или курсовая;
- ФИО и группы студента;
- ФИО и должности преподавателя для текущей дисциплины;
- дисциплины, номера и темы работы;
- города и года.

Вариант обязателен только при наличии вариантов в задании.

## Имя результата

Если пользователь не задал имя, применять безопасное имя без персональных данных сверх необходимого:

`Отчёт_ЛР_<номер>_<краткая-тема>.docx`

Не перезаписывать существующий DOCX без явного разрешения. При совпадении имени предложить новое имя или использовать версию `_v2` после согласования.

## Условия остановки

Отчёт готов только когда:

- все обязательные пункты задания закрыты доказательствами либо явно отмечены как заблокированные до решения пользователя;
- в режиме `execute-and-report` завершённый проект сохранён, обязательная сборка/запуск прошли и финальные тесты повторены;
- нет придуманных реквизитов, данных, результатов и источников;
- подписи, ссылки и нумерация согласованы;
- длинные таблицы корректно перенесены;
- титульный лист содержит проверенные реквизиты СПбПУ;
- валидатор не сообщает ошибок;
- визуально проверена каждая страница;
- итоговый файл имеет формат `.docx`.
